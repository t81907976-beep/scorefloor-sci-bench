## 为什么要做新的 Benchmark？

很多评测只看最终答案对不对，或者只看格式是否命中，这会把"会套模板"误判成"真的会解题"。

ScoreFloor-Sci-Bench 测的是更接近实际解题的能力：

| 维度 | 我们测什么 | 只看答案时容易漏掉什么 |
|-|-|-|
| 🎯 **结果** | 最终答复是否正确 | 过程对但结论错 |
| 🧠 **推理** | 能不能完成多步链路 | 单步对，不代表长链稳定 |
| ⚡ **效率** | 是否用更少的有效步骤完成任务 | 只会堆过程，不会精简 |
| 🔄 **一致性** | 同一题重复运行 5 次是否稳定 | 单次运气好，不代表可靠 |
| 📚 **学科泛化** | 是否能跨数、物、化、生四学科 | 只在单一学科上表现好 |

## 题库范围

面向 **数、物、化、生四学科**。当前入库 **25 道题**：

| 学科 | 题量 | 状态 |
|-|-:|-|
| 化学 | 15 | ✅ 可跑 |
| 物理 | 10 | ✅ 可跑 |
| 数学 | 0 | 🚧 模板就位，题目在排期中 |
| 生物 | 0 | 🚧 模板就位，题目在排期中 |

每道题都是**需要完整推导的多问计算题**，量级接近研究生课程习题与科研实操中的中间步骤
（等离子体漂移闭合、Marcus-Gerischer 重叠积分、Kummer 函数连接公式、粉末 XRD 系统消光……），
且最终答案唯一、可数值校验。每个 `.md` 文件包含题面、标准答案、解题思路（含基准步骤数 N₀），
以及三块评分规范（`Grading Criteria` / `Automated Checks` / `LLM Judge Rubric`）。

使用方式：

1. 用户配置自己的模型 API（OpenAI 兼容端点，或 Anthropic 原生 `/messages`）
2. 一条命令，每道题自动重复运行 5 次
3. 由统一的评分引擎 + 裁判模型自动判分
4. 汇总成单题分、学科分、全 Bench 总分，落盘到 `results/`

## 快速开始

核心链路**只依赖 Python 标准库（3.8+）**，无需 `pip install`。

```bash
# 1. 复制配置，填入你的 base_url / 模型名
cp config.example.json config.json

# 2. 填入密钥（.env 已在 .gitignore 中，不会被提交）
cat > .env <<'EOF'
MODEL_API_KEY=your-key
JUDGE_API_KEY=your-key
EOF
# 或临时 export，只对当前终端生效：
export MODEL_API_KEY=your-key    # 被测模型
export JUDGE_API_KEY=your-key    # 裁判模型（可与上面相同）

# 3. 预检：确认端点 / Token / 模型名都对
./scripts/run.sh --check
./scripts/run.sh --list-models

# 4. 跑（不带参数 = 全部题目，每题 5 次）
./scripts/run.sh
./scripts/run.sh --subjects chemistry             # 只跑化学
./scripts/run.sh --tasks test-化学05 --runs 5      # 只跑单题
./scripts/run.sh --dry-run                        # 不调 API，占位答复自检整条链路
```

`--dry-run` 用内置 mock 模型跑通「答题 → 代码判分 → 裁判判分 → 聚合」全链路，
建议先跑一次确认环境。

`config.json` 分 `model_under_test` 与 `judge` 两段，字段结构相同
（`provider` + `base_url` + `api_key_env` + `model`）。`provider` 默认 `auto`：
模型名含 Claude 系列标识时走 Anthropic 原生 `/messages`，其余走 OpenAI 兼容
`/chat/completions`。两种格式共用同一套重试与错误呈现逻辑，也都支持 `stream: true`。

> ⚠️ **裁判模型固定一个强模型，不要频繁换。** 换裁判后各次评测的判分口径不再可比，
> 应重跑全部题目而不是只补跑新题。同一批横向对比必须用同一裁判、同一套题、同样的 runs。

**多模型横评**：不用反复改配置，`--models` 传逗号分隔的模型名，
runner 依次用每个模型跑同一套题（裁判固定），各自落盘后输出对比表。

```bash
./scripts/run.sh --models "model-a,model-b,model-c" \
                 --subjects chemistry --runs 5 --concurrency 3
```

单个模型失败不中断整批，失败原因写进 `results/compare-<时间戳>.json`。

## 评分体系

三维度复合评分（完整推导与算例见 [docs/scoring-rules.md](docs/scoring-rules.md)）：

```
Bench Score = 成功率(60%) + 效率(20%) + 一致性(20%)
```

分层计算：

```
单次运行成功率  S_i = (最终答复分 + 步骤分 + 逻辑分) / 3
单任务成功率    S_success      = mean(S_1..S_5)
单任务效率      S_eff          = mean(S_i × E_norm_i),  E_norm = min(N₀/N_i / E_max, 1)
单任务一致性    S_consistency  = max(1 − CV, 0),        CV = σ/μ
单任务总分      S_task = S_success×0.6 + S_eff×0.2 + S_consistency×0.2
学科 / 全 Bench  S_total = mean(S_task)
```

- **成功率**：最终答复、关键步骤、逻辑链条是否成立
- **效率**：在保证正确性的前提下，步骤是否有效、简洁（得分 = 效率系数 × 成功率）
- **一致性**：同一题运行 5 次，结果是否稳定（5 次全错视为稳定，CV 记 0）

`E_max = 1.5`，即步骤精简到基准的约 67% 时效率项拿满分，避免跳步刷分。
另有一道**反向激励闸门**：步骤分为 0 的 run（一步未推、直接报结论）效率系数一律记 0——
不设这道闸门时，空转的 run 因"步骤最少"反而拿满效率分。

`python3 lib/scoring.py` 可复现规则文档第七节的算例。

## 三块评分规范的分工

每道题的评分规范拆成三块，代码侧与 LLM 侧不重叠：

| 块 | 负责 | 只做什么 |
|-|-|-|
| `Grading Criteria` | 这道题应满足什么 | 结果检查清单，对应标准答案关键节点 |
| `Automated Checks` | 代码能自动确认什么 | 只查最终答复硬证据（数值 / 单位 / 基准 / 关键词） |
| `LLM Judge Rubric` | 过程和逻辑怎么评 | 只评过程、概念、逻辑，专题定制分档 |

## 防蒙对：这套题为什么不好猜

唯一数值答案的题库有个天然弱点：**模型可以不解题、只把题面里的常数排列组合一下蒙对。**
这套题库为此专门做了四层设防，也是它与同类题库最实质的区别：

1. **量纲门**。数值必须与正确单位、正确基准语义在邻接窗内同时出现才计分。
   例如 `test-化学01` 的 k⁰ 要求 `cm/s` 与 "ECSA 基准" 都在窗内——
   否则模型复述一遍题面就能白拿这一项。
2. **陷阱位 / 反向项**。踩中常见错解分支要倒扣（化学题每题 2~6 条，每条 −0.25），
   或直接把对应检查项清零（如 `test-物理08` 只要保留增长支就清零）。
   匹配前先剪掉"假设 / 否证"从句，正确答复把错分支写出来再排除不会被误伤。
3. **语义绑定**。多个同量级数值并存时，要求数值绑到它所属的对象上。
   `test-化学12` 的两个峰面积必须各自绑到所属峰，否则"归属对调"的错解会白拿分。
4. **扰动审计**。用四个互补的扰动算子重跑全库，量化"答案无关也能拿到的分数地板"，
   地板过高的检查项会被收紧或降为零权重追溯项：

   | 算子 | 做什么 | 抓哪一类白拿分 |
   |-|-|-|
   | ① 数值扰动 | 所有数值乘一个因子，文字与格式一字不动 | 数值锚形同虚设的项 |
   | ② 翻符号 | 扰动因子额外取负 | 只看绝对值、不看符号的项 |
   | ③ 标签替换 | 只把结论标签换成反面表述 | 纯文字结论判据（数值探针测不到） |
   | ④ 复述题面 + 拒答 | 输入 = 题面原文 + 一句"无法给出答案" | 存在性判据、把题面常数当结论锚 |

   算子 ①② 在 `scripts/audit_false_positive.py`（`--flip-sign` 开第二档），
   ③④ 分别是 `audit_label_swap.py` 与 `audit_restate_refuse.py`。

另有一层工程侧的容错：判分入口做 `raw` / LaTeX 去壳 / 再去下标**三档重判取最优**，
只放宽表现形式（`\boxed{}`、`\mathrm{}` 单位壳、`\times`、硬空格），
不动任何数值与符号——把"换个写法就判错"的假阴性挡在判分之外。

## 跑一遍的真实开销

**这不是"一条命令几分钟"的事，请先看这组实测数据。**
下面这组分布来自 41 次成功答题的落盘记录（题目为本题库化学题的长思考题）：

| 指标 | 中位 | p90 | max |
|-|-:|-:|-:|
| 单次答题耗时（秒） | 361 | 896 | 2,654 |
| completion_tokens | 9,042 | 62,242 | 96,094 |
| 思维链字符 | 23,251 | 132,565 | 195,155 |
| 判分实际读到的正文字符 | 1,597 | 2,808 | 4,808 |

按中位数推算全量（25 题 × 5 次 = 125 次答题）：

- **串行约 12.5 小时**；按 p90 约 31 小时。`--concurrency 3` 也要 4 小时以上。
- 注意最后两行的比例：**思维链约是判分正文的 15 倍，也就是 ~95% 的输出 token
  烧在判分根本不会读的思维链上。** 这是成本结构里最关键的一条。
- 调用量 = 模型数 × 题数 × runs × 2（答题 + 判分）。

因此长思考题**必须走 SSE 流式**：非流式会被反向代理 / 网关按空闲超时切断
（表现为 HTTP 504），流式下 token 持续到达才能拿回完整的长答复。
`scripts/fetch_single.py` 默认即为流式，并把抓取与判分拆成两段——
抓一次答复可以反复重判（改了 Rubric 不用重新烧 token），某个模型超时也只重抓它自己。

```bash
python3 scripts/fetch_single.py test-化学09 --models "model-a,model-b" \
    --tag 化学09 --max-tokens 32000 --timeout 2400 --attempts 3
python3 scripts/score_single.py test-化学09 --tag 化学09 --judge <judge-model> \
    --sources single-化学09-<时间戳>.json
```

长跑时可用 `python3 scripts/progress.py -w` 看实时进度面板（只解析日志，不干扰跑测）。

## 设计原则

1. **语义评分 > 格式匹配**，关注答案、过程和逻辑
2. **统一口径**，四个学科共用同一套评分框架
3. **重复运行**，每道题跑 5 次，降低偶然性
4. **防蒙对**，量纲门 + 陷阱位 + 语义绑定 + 扰动审计，压低"答案无关也能拿分"的地板
5. **可追溯**，每个分数都能回到原始输出和逐项判分记录

题库连标准答案与 `grade()` 一起完整开源，用户可以完全看懂每一分是怎么给的。
代价是它不适合用来做对外权威榜单——题面、答案、判分窗都公开时，
分数只对"不曾针对本题库训练过"的模型有意义。
